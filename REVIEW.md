# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | Startup / `init_db` (lines 22-23) | No indexes created on startup; only MongoDB's default `_id` index existed. No uniqueness enforced on `employees.emp_code` or `attendance_logs.(emp_code, date)`. | Duplicate employees and multiple punch-ins on the same day could be inserted; list queries performed full collection scans (`COLLSCAN`). | Created unique indexes on `employees.emp_code` and `attendance_logs.(emp_code, date)` and supporting indexes on `attendance_logs.(date, emp_code)`, `attendance_logs.(emp_code, punch_in)`, `employees.(department, emp_code)`, and `employees.joined_on`. |
| 2 | `compute_late_minutes` (lines 33-37) | Integer division before grace check: `minutes = int((punch_in - start).total_seconds() / 60)` then `minutes if minutes > 10 else 0`. Fails R2 boundary where punch-in is strictly > 10:00 (600s) after shift_start. Also did not truncate seconds before calculation. | Punching in at 09:40:01 for a 09:30 shift is 601s late; `int(601/60)` is 10, so `10 > 10` evaluates to False and incorrectly returns 0 instead of 10. | Truncated instants to whole seconds first, checked `diff_seconds > 600`, and if true computed `late_minutes = diff_seconds // 60`. |
| 3 | `compute_overtime` (lines 44-48) | Missing Rule R3 $\ge 30$-minute threshold check (`max(0, minutes)`). Returned overtime for 1–29 minutes. Also subtracted naive UTC `punch_out` from aware IST `end`, raising a `TypeError`. | Punch-out at 18:45 on an 18:30 shift returned 15 overtime minutes instead of 0; or raised `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Enforced R3 threshold: overtime is counted only if $\ge 30$ minutes, otherwise 0; normalized datetime timezone offsets before difference calculation. |
| 4 | `compute_work_hours` (lines 40-42) | Used Python's built-in `round()`, which applies banker's round-half-to-even rounding instead of arithmetic round-half-up required by R4 and R8. | Duration of 4.225 hours rounded to 4.22 instead of 4.23, failing contract precision checks. | Implemented `round_half_up` helper using `Decimal` with `ROUND_HALF_UP`. |
| 5 | `EmployeeIn` model (lines 53-61) | Allowed identical `shift_start` and `shift_end` (0-minute shift); accepted arbitrary strings for `emp_code` without pattern `^EMP\d{4,6}$`; accepted malformed email and date strings. | `POST /employees` with `"shift_start": "09:30", "shift_end": "09:30"` returned 201 Created; downstream shift duration calculation produced zero division errors. | Added model validator `shift_start != shift_end`, regex on `emp_code`, email validation, and strict `YYYY-MM-DD` date validation. |
| 6 | `PunchInIn` model (lines 63-67) | `punched_at: Optional[int]` accepted unix seconds (e.g. 10 digits) without validating millisecond range; `status: str = "PRESENT"` allowed arbitrary status strings. | Payload `{"punched_at": 1700000000}` (seconds) was accepted and produced corrupted dates; invalid status like `"VACATION"` was accepted. | Added strict `EpochMillis` validation enforcing $10^{12} \le t \le 10^{13}$ and constrained `status` to `PresenceStatusEnum` (`PRESENT`, `WFH`, `ON_DUTY`). |
| 7 | `health` endpoint (lines 72-74) | Returned `{"status": "ok"}` unconditionally with HTTP 200 without verifying MongoDB connectivity. | `GET /health` returned 200 OK even when MongoDB was stopped or unreachable. | Added `client.admin.command("ping")`, returning HTTP 503 Service Unavailable on connectivity failure. |
| 8 | `create_employee` (lines 77-85) | Non-atomic check-then-insert (`find_one` then `insert_one`) without a unique index on `emp_code`. Also saved naive `datetime.now()` for `created_at`. | Concurrent requests with the same `emp_code` resulted in duplicate records or unhandled database exceptions instead of HTTP 409. | Relied on unique index `emp_code_1` to reject duplicates with 409 and stored timezone-aware UTC datetime. |
| 9 | `list_employees` pagination skip (line 93) | Off-by-one pagination skip: `skip = page * page_size`. For `page=1, page_size=20`, `skip = 20`, completely skipping the first 20 records. | Calling `GET /employees?page=1` returned the 21st through 40th employees, omitting page 1 entirely. | Corrected skip calculation to `skip = (page - 1) * page_size`. |
| 10 | `list_employees` total count & sorting (lines 94-95) | `total = db.employees.count_documents({})` ignored the `department` filter (violating R10: "total always reflects the filters"). Additionally, omitted `emp_code` ascending sort. | `GET /employees?department=Sales` returned paginated Sales employees, but `total` reported company-wide headcount; items were returned in unordered natural insertion sequence. | Passed filter dictionary `q` to `count_documents(q)` and added `.sort("emp_code", 1)`. |
| 11 | `punch_in` unknown employee crash (lines 101, 113) | Queried `emp = db.employees.find_one(...)` without checking for `None`. Accessing `emp["shift_start"]` raised an unhandled `TypeError`. | Calling `POST /attendance/punch-in` with an unregistered `emp_code` crashed with HTTP 500 Internal Server Error instead of HTTP 404. | Added explicit check `if not emp: raise HTTPException(404, "Employee not found")`. |
| 12 | `punch_in` overnight shift logic (lines 102-103) | Assigned attendance date directly from punch timestamp `ts.date().isoformat()`. Ignored Rule R1 for overnight shifts (`shift_end <= shift_start`). | For a 22:00–06:00 overnight shift, punching in at 05:30 IST was assigned to the current day instead of the shift that started the previous evening. | Implemented R1: if `shift_end <= shift_start` and punch time is strictly before `shift_end`, attendance date is assigned to the previous calendar day. |
| 13 | `punch_in` concurrency race condition (lines 104-118) | Non-atomic `find_one` followed by `insert_one` without a unique compound index on `(emp_code, date)`. | Simultaneous punch-in requests for the same employee and date both passed the check, creating duplicate records for the same day. | Enforced unique compound index on `(emp_code, date)` and caught `DuplicateKeyError` to return HTTP 409 Conflict. |
| 14 | `list_attendance` in-memory sorting & pagination (lines 144-147) | Loaded the entire collection into Python memory via `list(db.attendance_logs.find(q))`, then performed Python-side sorting and slicing instead of using database `.sort()`, `.skip()`, and `.limit()`. | Explain plan exhibited full collection scans; latency and memory usage escalated linearly with dataset size. Additionally, secondary sort by `emp_code` was missing. | Performed pagination and compound sorting directly in MongoDB using `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`, supported by compound index `(date, -1), (emp_code, 1)`. |
| 15 | `list_attendance` inverted date range validation (lines 136-141) | Did not validate `date_from <= date_to`. Executed an impossible range query and returned 200 OK with empty items instead of HTTP 422. | Calling `GET /attendance?date_from=2026-03-31&date_to=2026-03-01` returned 200 OK with `{"items": [], "total": 0}` instead of HTTP 422. | Added validation `if date_from and date_to and date_from > date_to: raise HTTPException(status_code=422)`. |
| 16 | API response serialization & `_id`/`id` leakage (lines 119-120, 148-149) | Injected `"id": str(inserted_id)` into attendance records and returned Python `datetime` objects for `punch_in`. | Responses exposed an `"id"` field and ISO datetime strings, violating `openapi.yaml` and `DATA_MODEL.md` (attendance records have no ID; timestamps must be integer epoch milliseconds). | Created serializers that omit `_id`/`id` and convert BSON datetimes to integer epoch milliseconds. |
| 17 | Timezone handling & naive timestamps (lines 22, 25, 102) | `MongoClient` was initialized without `tz_aware=True`, and `datetime.fromtimestamp()` generated naive datetimes in the host's local timezone. | Punches near UTC midnight were assigned to incorrect calendar dates depending on server host timezone. | Initialized MongoClient with `tz_aware=True`, explicitly converted all timestamps using `ZoneInfo("Asia/Kolkata")` (IST, UTC+05:30), and stored UTC BSON datetimes. |

Also note anything you looked at and decided was **not** a defect, and why.

- **PyMongo BSON Datetimes in UTC**: PyMongo stores instants as UTC BSON datetimes in MongoDB. Converting epoch millisecond timestamps to UTC `datetime` on write and converting BSON datetimes back to integer epoch milliseconds on read is intentional and correct per `DATA_MODEL.md`.
- **Query Parameter Aliasing (`alias="from"`)**: In `GET /analytics/departments/{department}/trend`, the parameter name is `from`. Because `from` is a reserved keyword in Python, declaring `from_date: str = Query(..., alias="from")` is the idiomatic FastAPI practice, not a defect.
- **Unseeded `half_day` or `history` fields**: Sample documents sometimes omit `half_day` or `history`. Treating absent `half_day` as `false` and absent `history` as an empty list `[]` adheres to the specification ("Seeded records may omit history or half_day; treat them as empty and false").
