# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | Startup / `init_db` | No indexes created on startup; only MongoDB's default `_id` index existed. No uniqueness enforced on `employees.emp_code` or `attendance_logs.(emp_code, date)`. | Duplicate employees and multiple punch-ins on the same day could be inserted; list queries performed full collection scans (`COLLSCAN`). | Created unique indexes on `employees.emp_code` and `attendance_logs.(emp_code, date)` and supporting indexes on `attendance_logs.(date, emp_code)`, `attendance_logs.(emp_code, punch_in)`, `employees.(department, emp_code)`, and `employees.joined_on`. |
| 2 | Timezone handling (`epoch_to_ist_date` / datetime helpers) | Datetime conversions used naive `datetime.fromtimestamp()` or host local timezone instead of enforcing Indian Standard Time (`Asia/Kolkata`, UTC+05:30). | Punches around 00:00–05:30 UTC were assigned to the incorrect calendar date depending on the server host's timezone. | Explicitly bound all date and timestamp conversions to `ZoneInfo("Asia/Kolkata")` and converted BSON UTC datetimes at API boundaries. |
| 3 | Input models (`EpochMillis` / timestamp validation) | Request schemas accepted floating-point timestamps, strings, and second-based unix timestamps (e.g. 10 digits) without strict type and range validation. | Payload `{"punched_at": 1700000000}` (seconds) or `{"punched_at": 1700000000000.5}` (float) passed Pydantic validation and corrupted BSON date conversions. | Added strict integer millisecond validation (`int`, non-boolean, range $10^{12} \le t \le 10^{13}$) rejecting floats, strings, and seconds with HTTP 422. |
| 4 | Employee validation (`EmployeeIn`) | Permitted identical `shift_start` and `shift_end` (0-length shift); accepted invalid `emp_code` formats without format constraints; accepted malformed emails and dates. | POST `/employees` with `"shift_start": "09:30", "shift_end": "09:30"` returned 201 Created, causing downstream shift duration calculations to fail. | Enforced `shift_start != shift_end`, regex `^EMP\d{4,6}$` on `emp_code`, email validation, and strict `YYYY-MM-DD` date validation. |
| 5 | Overnight shift handling (`punch_in` / R1) | Attendance date was determined solely by the calendar day of punch-in, ignoring overnight shifts where `shift_end <= shift_start`. | On a 22:00–06:00 overnight shift, a punch-in at 05:30 IST was assigned to the current day instead of the shift that started the previous evening. | Implemented Rule R1: when `shift_end <= shift_start` and punch-in time is strictly before `shift_end`, attendance date is set to the previous calendar day. |
| 6 | Late calculation (`compute_late_minutes` / R2) | Subtracted the 10-minute grace period from the late duration (`late_minutes = diff - 10`). Did not truncate seconds before calculation. | Punching in at 09:45:00 for a 09:30:00 shift yielded 5 late minutes instead of 15 (R2 specifies full elapsed minutes from `shift_start` once the 10-minute threshold is exceeded). | Updated calculation: if elapsed time > 10 minutes, `late_minutes = floor((punched_sec - shift_start_sec) / 60)`. Truncated instants to whole seconds first. |
| 7 | Rounding method (`round` / R4, R8) | Used standard Python `round()`, which applies banker's round-half-to-even rounding. | Work hours like 4.225 rounded to 4.22 instead of 4.23, violating R4 and failing contract precision requirements. | Implemented `round_half_up` helper using `Decimal(str(val)).quantize(Decimal(exp), rounding=ROUND_HALF_UP)`. |
| 8 | Concurrency in punch-in (`POST /attendance/punch-in`) | Relied on a non-atomic `find_one()` check followed by `insert_one()`. | Two simultaneous punch-in requests for the same employee and date both passed the check, causing duplicate records or unhandled 500 errors. | Leveraged MongoDB unique compound index `(emp_code, date)` and caught `DuplicateKeyError` to return HTTP 409 Conflict. |
| 9 | Concurrency in punch-out (`POST /attendance/punch-out`) | Fetched the latest open record, verified `punch_out is None` in Python, and called `update_one()`. | Concurrent punch-out requests on the same open record both succeeded, yielding multiple 200 responses instead of one 200 and subsequent 409s. | Used atomic `find_one_and_update({"_id": rec["_id"], "punch_out": None}, ...)`; if no document was matched, returned HTTP 409 Conflict. |
| 10 | Concurrency in regularization (`PATCH /attendance/{emp_code}/{date}`) | Read document, appended history entry in memory, and wrote back with `update_one()` without concurrency control. | Concurrent patch requests resulted in lost updates where one request's history entry overwrote the other's. | Applied atomic update with filter checking current document state and `$push` on `history` field; returned 409 on concurrent modification. |
| 11 | Department pagination count (`GET /employees` / R10) | `total` in response executed `db.employees.count_documents({})` without applying the department filter. | Requesting `GET /employees?department=Sales` returned paginated Sales employees, but `total` reported the total count of all employees in the company. | Passed the active department filter dictionary to `count_documents(filter_q)` so `total` accurately reflects filtered records. |
| 12 | Inverted date range validation (`GET /attendance`) | Accepted `date_from > date_to` without validation, executing an impossible range query and returning 200 OK with empty items. | Calling `GET /attendance?date_from=2026-03-31&date_to=2026-03-01` returned 200 OK instead of HTTP 422. | Added validation `if date_from and date_to and date_from > date_to: raise HTTPException(status_code=422)`. |
| 13 | Health check (`GET /health`) | Returned `{"status": "ok"}` unconditionally with HTTP 200 without checking database connectivity. | Endpoint returned 200 OK even when MongoDB was unreachable or crashed. | Added `client.admin.command("ping")` within try/except block, returning HTTP 503 Service Unavailable on connectivity failure. |
| 14 | MongoDB `_id` leakage in responses | Returned raw MongoDB query dictionaries directly, exposing internal `_id` fields in JSON responses. | Responses contained `"_id": "64b..."`, violating the contract requirement that `_id` must never appear in API responses. | Created document serializer functions (`serialize_employee_doc`, `serialize_attendance_doc`) that omit `_id` and map only contract fields. |

Also note anything you looked at and decided was **not** a defect, and why.

- **PyMongo BSON Datetimes in UTC**: PyMongo stores instants as UTC BSON datetimes in MongoDB. Converting epoch millisecond timestamps to UTC `datetime` on write and converting BSON datetimes back to integer epoch milliseconds on read is intentional and correct per `DATA_MODEL.md`.
- **Query Parameter Aliasing (`alias="from"`)**: In `GET /analytics/departments/{department}/trend`, the parameter name is `from`. Because `from` is a reserved keyword in Python, declaring `from_date: str = Query(..., alias="from")` is the idiomatic FastAPI practice, not a defect.
- **Unseeded `half_day` or `history` fields**: Sample documents sometimes omit `half_day` or `history`. Treating absent `half_day` as `false` and absent `history` as an empty list `[]` adheres to the specification ("Seeded records may omit history or half_day; treat them as empty and false").
